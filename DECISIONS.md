| DEC-001 | IFSC display | Mask the bank **account number** only (`XXXX XXXX 4471`). Show the **full IFSC** in the vendor master view, invoice evidence and comparison panel. An IFSC is a public branch identifier, not a secret, and T-03 depends on the reviewer seeing `ICIC0005678` against `HDFC0005512`. | DEC-002 | Demo reset on the public deployment | Specified in PRD v1.2 FR-116 and §8.8. **Exposure:** the "Reset demo data" button and its Next.js route `frontend/app/api/demo/reset/route.ts` are intentionally public so the live demo can be reset; this is acceptable only because every record reset touches is synthetic. **Token:** backend `POST /api/demo/reset` requires header `X-Demo-Reset-Token` matching `DEMO_RESET_TOKEN` (required backend env var; backend refuses to start without it; constant-time compare). The token is held only in server-side env vars (no `NEXT_PUBLIC_` prefix), added by the Next.js route, and never reaches browser code. Its only job is to ensure every reset request reaches the backend through the Next.js route; it does not restrict who can press the button and does not by itself enforce confirmation or rate limits. The backend independently enforces both on every request. The Next.js route only injects the token and forwards. **Confirmation:** user types `RESET`; body `confirm` must equal `RESET`, else `400`. **Rate limits:** 1 successful reset per 30 seconds; 5 rejected attempts per IP per 15 minutes; else `429`. **Atomicity:** one `BEGIN IMMEDIATE` transaction (delete, reload `fixtures-v1`, FK check, count check, insert `success` row, commit); any error rolls back fully; uploaded files deleted only after commit. **Reset history (`demo_resets`):** `reset_id`, `requested_at`, `outcome` (`success` / `rejected` / `rate_limited` / `failed`), `requester_label`, `failure_reason` (required unless `success`), `detail`; UPDATE/DELETE blocked by triggers; never cleared by reset. `rejected`, `rate_limited` and `failed` rows are written in a separate transaction after rollback, so failures persist. **Responses:** 200 / 400 / 401 / 429 / 500. | Resolved |

| DEC-011 | Per-IP reset limit behind the Next.js proxy | Every UI reset reaches the backend from the Next.js server's address, so FR-116's "5 rejected attempts per IP per 15 minutes" collapsed into one global bucket: one visitor sending bad confirmations could lock out the interviewer. Resolution: `frontend/app/api/demo/reset/route.ts` forwards the browser's address in `X-Client-IP`, taken from the platform's forwarded headers (`x-real-ip`, then the first `x-forwarded-for` entry). App Router handlers do not expose the socket address, so when neither header exists nothing is forwarded. The backend uses `X-Client-IP` (if it parses as an IP address) for the rejected-attempt bucket **only when the request carries a valid `DEMO_RESET_TOKEN`**; otherwise it uses the socket address. Only the trusted server route holds the token, so the header is believed exactly when it is needed, and tokenless direct callers are bucketed by their real address. The 30-second successful-reset limit stays global: it protects the database, not a client. `X-Client-IP` is never logged and never stored in `demo_resets.detail`. Residual risk (verified locally): the Next.js server passes a client-supplied `x-forwarded-for` through unchanged, so on a host with no proxy in front a visitor could rotate it to dodge the per-visitor bucket. Vercel overwrites these headers at its edge, so the deployed demo is not affected; the worst case elsewhere is the pre-DEC-011 behaviour plus evasion of a limit that protects only synthetic data. The production answer is platform-level rate limiting with trusted-proxy configuration, which is out of scope for this prototype. | Resolved |

| DEC-019 | Value flagged for review (Day 8) | **Proposed by implementation, pending review. Not reviewed or approved by the product owner.** Per decided run, one exposure amount in integer paise. *Formulas:* `PO_BALANCE_EXCEEDED` = previously approved + this invoice's taxable value - PO ceiling; `QUANTITY_EXCEEDS_PO` = excess quantity x PO unit price, summed over lines; `UNIT_PRICE_VARIANCE` = (invoice unit price - PO unit price) x invoice quantity, positive terms only; `ARITHMETIC_MISMATCH` = |printed total - computed total|, with the computed total built as the E4 equation builds it; `CONFIRMED_DUPLICATE`, `VENDOR_BLOCKED`, `BANK_DETAILS_MISMATCH` = the full invoice total; every other code = 0. *Max, not sum:* an invoice's exposure is its largest single contribution, because several codes can describe one problem (T-02: quantity ₹20,000 and balance ₹19,000 describe the same overrun, so it counts once at ₹20,000). *Flagged, not resolved:* codes count as flagged at decision time, including codes a reviewer later overrode (the stored decision's codes plus each override's `codes_overridden`). PO-based amounts use the PO state stored with the decision, so a code added later by the commit recheck can contribute zero; on T-25a the full-total bank code drives the amount anyway. Invoices with no valued discrepancy are left out of the breakdown. Ties break by severity order. *Wording:* labelled "Value flagged for review" and described as the value of discrepancies surfaced for a person to resolve, never as a financial result. Code is in `app/services/exposure.py`, served in `GET /api/dashboard` as `value_flagged_for_review`. *Reasoning:* the max rule avoids double counting one discrepancy, and counting overridden codes reflects what the system surfaced rather than what reviewers later decided. **Amendment (Day 8B), proposed by implementation, pending review, not approved by the product owner:** the contributing codes are split into two buckets, each code in exactly one, reported as two separate figures. *Measured discrepancy* (`PO_BALANCE_EXCEEDED`, `QUANTITY_EXCEEDS_PO`, `UNIT_PRICE_VARIANCE`, `ARITHMETIC_MISMATCH`) is shown as "Discrepancy value flagged". *Invoice value at risk* (`CONFIRMED_DUPLICATE`, `VENDOR_BLOCKED`, `BANK_DETAILS_MISMATCH`) is shown as "Invoice value held for review". Max-not-sum now applies within each bucket independently, so one invoice can count in both. The figures are never combined, in the API (`value_flagged_for_review` carries `discrepancy` and `held`, and no combined total) or on the page. *Reasoning:* they measure different things. The first is an error the rules computed; the second is the gross value of an invoice stopped before payment, which already contains any computed error on the same invoice. Adding them would double count that error and mix a discrepancy with a gross amount. | Proposed, pending review |

| DEC-021 | Resolution drafts on HOLD and REJECT (Day 10) | **Proposed by implementation, pending review. Not reviewed or approved by the product owner.** Every HOLD or REJECT decision can render a ready-to-send message per recipient. *Deterministic:* the drafts are string templates in `backend/app/drafts/templates.py`, one per reason code, filled by `app/drafts/fields.py` from the stored decision's evidence, PO detail, duplicate matches and candidate list, plus the vendor master row the decision identified. There is **no model call** anywhere in the feature, and `tests/test_drafts.py` fails if the package imports an HTTP, SMTP or model client. The same decision always renders a byte-identical draft (`test_drafts_are_byte_identical_when_generated_twice`). No template contains a figure, a threshold, a person's name, an email address or a phone number; money is formatted once, through the existing Indian-grouping formatter (`app.rules.common.rs`). A placeholder with no value raises `DraftError` and the endpoint answers 422; a draft never prints a blank, a "None" or a guessed value. *Routing, one draft per recipient, not per code:* VENDOR for `PO_BALANCE_EXCEEDED`, `QUANTITY_EXCEEDS_PO`, `UNIT_PRICE_VARIANCE`, `LINE_ITEM_UNMATCHED`, `ARITHMETIC_MISMATCH`, `TAX_REGIME_MISMATCH`, `MISSING_REQUIRED_FIELD`, `POSSIBLE_DUPLICATE`, `POSSIBLE_REVISION` and `CONFIRMED_DUPLICATE` (which states that the original was already approved and this copy will not be paid); BUYER_INTERNAL for `PO_NOT_FOUND`, `PO_INFERRED`, `VENDOR_NOT_FOUND`, `VENDOR_BLOCKED`, `LOW_EXTRACTION_CONFIDENCE` and `UNSUPPORTED_DOCUMENT`; TRUSTED_CONTACT for `BANK_DETAILS_MISMATCH`. Within a draft the highest-severity code leads and the rest follow as numbered items, ordered by severity, then the reason-code registry's stage order, then the code name. *Bank-details draft:* addressed to "Verified contact on the vendor master" and nothing else. The trusted contact's name, phone and email are never read by the drafts code (explicit column whitelist) and never appear in the response, extending DEC-008 from `GET /api/vendors` to this endpoint; no contact detail printed on the invoice is addressed or quoted; both account numbers appear as their last four digits with the IFSC in full, exactly as DEC-001 and FR-041 require, because the draft reuses the masked evidence the rule recorded; the draft asks the vendor to confirm through the channel already recorded on the vendor master, states that payment is on hold until then, and the UI carries the note "Send only through the contact on file. Do not reply to the invoice." *Not persisted, never sent:* `GET /api/runs/{run_id}/drafts` generates the drafts from the stored decision on every request. No schema change, no new table, no write, no audit event (`test_the_endpoint_writes_nothing`). There is no send path of any kind: no email, no SMTP, no third-party API, no Send button and no `mailto:` link. APPROVE returns `[]` and the card renders nothing; a run that is not yet decided returns 409. *Wording:* `tests/test_draft_labels.py` extends the FR-034 claim scan to the draft templates and bans "verified" applied to a GSTIN or to account details; "Verified contact on the vendor master" is the one permitted use of the word. *Reasoning:* flagging an exception is only half the work, and the figures needed to resolve it are already in the evidence, so a draft adds no new judgement and no new trust assumption. It stays deterministic because a generated message that quietly restates a figure differently from the decision would be worse than no message. It is not persisted because a stored draft would drift from the decision it describes, and nothing is sent because sending is a separate, auditable capability this prototype does not claim. | Proposed, pending review |
